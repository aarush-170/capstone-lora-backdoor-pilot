## 5. Conflicts and corrections to settle first
1. **WSD versions differ.** `CONTEXT_REVIEW2_CONCLUSIONS.md` section 3 describes WSD v1/v2 (sum over q, k, v, o at layer 21; 97% accuracy on 50 + 50 held out; no AUROC). v3 (arXiv 2602.15195v3, 2026-04-07, "Detecting Backdoored LoRAs from Weights Alone") **concatenates the four projections into 20 numbers** and reports accuracy 1.00 and ROC-AUC 1.00 on three model families **[Reported: read through a text-extracting fetch, not eyeballed]**. Our Review 1 slide ("20 spectral features ... 100%") matches v3. So (a) the planned slide fix "100% to 97%" must name the version; (b) the grouped-query summing problem (k and v are 256 x 2048) exists only for the v2 sum; (c) the plan's "features per module then average across modules" produces 5 numbers, whereas v3 gives 20 (per projection). **Seat C must decide which version `wsd_aligned` follows and record it (suggestion: v3 per-projection, because it is the later version, the authors' code produces 4 x 5 = 20 features, and it avoids the summing problem).** Eyeball the v3 PDF before quoting any number.
2. **PADBench sizes.** 536,888,520 bytes is the **rank-256** q+v fp32 size (32 layers x 2 x (4096x256 + 256x4096) x 4 bytes). Earlier notes of ours ("about 537 MB per adapter", "20-adapter slice about 11 GB") apply only to rank-256 sets; a rank-16 adapter is about 33.5 MB (about 0.7 GB per 20). Corrected in `tracking/` files.
3. **The paper vs code energy formula** (sigma1 / sum sigma vs sigma1^2 / sum sigma^2): follow the code and record it (already DEC-010).
4. **The plan's "tonight" schedule is aggressive** (all 21 adapters and the verdict tonight, three seats): the critical path is `ref_clean` -> `ref_stats.json` -> evasive runs, and the penalty has never run on a GPU. Do the GPU smoke test (10 steps with and without the penalty) **before** committing the whole queue; the plan's own cut order applies (drop lambda = 1 first; never skip the validity check).
